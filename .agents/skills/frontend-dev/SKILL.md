# Railsフロントエンド開発

## 基本方針

このプロジェクトでは、Rails標準のViewとHotwireを中心にフロントエンドを実装する。

原則として以下を使用する。

- HTML: ERB
- 動的な画面更新: Turbo
- JavaScriptが必要なUI: Stimulus
- スタイリング: プロジェクトで既に採用されている方法を使用する

ReactやVueなどの新しいフロントエンドフレームワークを、
明示的な指示なしに導入しないこと。

既存のRails / Hotwireの仕組みで実現可能な場合は、
JavaScriptを過剰に追加しないこと。


## 作業開始前

実装・変更を行う前に以下を実施する。

1. 関連する要件を確認する
2. 関連する既存Viewを確認する
3. Controllerから渡されるデータを確認する
4. routesを確認する
5. 既存のCSS・UIコンポーネントを確認する
6. Turbo / Stimulusの既存実装があれば、そのパターンを確認する

既存のデザイン・命名規則・実装パターンを優先すること。


## View

Rails Viewは原則として以下に配置する。

`app/views/`

例:

- `app/views/users/index.html.erb`
- `app/views/users/show.html.erb`
- `app/views/users/new.html.erb`
- `app/views/users/edit.html.erb`

Controllerから渡されたインスタンス変数を使用して表示する。

View内に複雑なビジネスロジックを書かないこと。


## Partial

複数箇所で使用するUIや、Viewが大きくなった場合はPartialへの分割を検討する。

例:

`app/views/users/_user.html.erb`

呼び出し例:

`<%= render user %>`

ただし、小さなUIまで過剰にPartial化しないこと。


## Form

フォームはRailsの標準機能を優先する。

原則として `form_with` を使用する。

例:

`<%= form_with model: @user do |form| %>`

バリデーションエラーが発生した場合は、
ユーザーが原因を理解できる形でエラーメッセージを表示する。

二重送信など、明らかな誤操作についても必要に応じて対策する。


## Turbo

ページ全体のJavaScript実装を追加する前に、
Turboで実現できないか検討する。

以下のような処理ではTurboの利用を優先する。

- フォーム送信
- 一覧の追加・削除
- 部分的な画面更新
- モーダル等の部分表示
- サーバー処理後のUI更新

必要に応じて以下を使用する。

- Turbo Drive
- Turbo Frames
- Turbo Streams

ただし、単純な画面で不必要にTurbo Frameを使用しないこと。


## Stimulus

ブラウザ上でJavaScriptによる状態管理や操作が必要な場合はStimulusを使用する。

Controllerは原則として以下に配置する。

`app/javascript/controllers/`

Stimulusを使用する例:

- ボタンによる表示・非表示
- 入力内容に応じたUI変更
- モーダル
- ドロップダウン
- 文字数カウント
- コピー処理
- クライアント側の簡単な操作

サーバー側で処理できるビジネスロジックをStimulusに移さないこと。


## CSS

既存プロジェクトのCSS構成・命名規則を確認してから変更する。

新しいスタイリングライブラリを勝手に追加しないこと。

既存クラスを再利用できる場合は再利用する。

変更対象以外の画面に影響を与える可能性がある
広範囲なCSS変更は避ける。


## Controllerとの責務分離

View:

- 表示
- フォーム
- UI構造

Stimulus:

- ブラウザ上の軽量なインタラクション

Controller:

- リクエスト処理
- Modelとの連携
- Viewへ渡すデータの準備

Model:

- データ
- バリデーション
- ビジネスルール

責務を混在させないこと。


## UI/UX

新しい画面を作成するときは以下を確認する。

- ユーザーが次に何をすればよいか分かる
- ボタンの役割が明確
- エラー内容が理解できる
- データが存在しない場合の表示がある
- 処理成功時に適切なフィードバックがある
- 既存画面とデザインが大きく乖離していない

必要に応じてスマートフォン表示も確認する。


## アクセシビリティ

可能な限りセマンティックなHTMLを使用する。

クリック操作が必要な要素について、
単なる `div` より `button` や `a` が適切な場合はそちらを使用する。

フォームには適切なlabelを設定する。

画像には必要に応じてaltを設定する。


## テスト

フロントエンド変更後は関連するテストを実行する。

既存プロジェクトに以下のテストが存在する場合は活用する。

- View test
- Controller / Request test
- System test

重要なユーザーフローを変更した場合は、
必要に応じてSystem testを追加・更新する。

テストが失敗した場合は、

1. エラーを確認
2. 原因を調査
3. 修正
4. 再実行

を行うこと。


## 動作確認

実装後は可能な範囲で以下を確認する。

1. 正常に画面が表示される
2. フォームが正常に送信できる
3. バリデーションエラーが表示される
4. Turboによる更新が正常に動作する
5. Stimulusを使用した場合、その操作が正常に動作する
6. 既存画面に意図しない影響がない


## バックエンド変更が必要な場合

フロントエンド機能を実現するためにController、Model、
routes、DB等の変更が必要になった場合は、
関連するバックエンドSkillも使用すること。

フロントエンド側だけに無理な処理を追加して解決しないこと。


## 完了条件

以下を満たした場合に作業完了とする。

- 要件を満たすUIが実装されている
- 既存デザインとの一貫性がある
- 必要なフォーム・エラー表示が実装されている
- Turbo / Stimulusが適切に使用されている
- 不必要なJavaScriptが追加されていない
- 関連テストが通っている
- 既存画面への意図しない影響がない
- 最終的な差分を確認している
